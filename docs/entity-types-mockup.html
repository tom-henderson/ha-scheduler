Four new entity types for the day timeline

Mockups for the entities proposed in issue #8 — switch, climate, media player and stateless automation triggers — drawn in the card's real visual language so the fit (and the work each one takes) is obvious at a glance.

issue #8 The card is already data-driven: every type lives in TYPE_REGISTRY, so new device families should slot in without touching the engine or the drag logic. These four test that promise — three keep it, one bends it.

Ordered by how much is genuinely new

Data only

A registry entry + a target-domain filter. No new UI. Switch.

Richer state

States gain editable parameters; the segment popover grows fields. Climate, Media.

New bar shape

Points in time instead of ranges — a second kind of bar. Triggers.

Switch

Data only

A helper toggle (input_boolean or switch) flipped on a schedule to trigger other automations. Behaviourally identical to Water — two states, same segment editor — so it's a pure registry addition.

Nothing in the UI. Add one entry to const.py and one line to the card's target-domain map so the entity picker offers helper toggles.

Climate

Richer state

Each active state is a preset — HVAC mode, target temperature and fan mode together. Segments read as “Heat 21°” and colour by mode, and the segment editor grows a parameter block. This introduces the general idea of states that carry data.

daily-schedule-card · climate bar

00:00 06:00 12:00 18:00 24:00
Living room thermostat
climate.living_room
Heat 21°
Eco 17°
Heat 22° · fan hi

What changes

A state's data becomes user-editable through a param schema declared on the type. The segment editor renders those params — the only genuinely new widget is a temperature stepper.

  • Segment fill colours by HVAC mode (heat / cool / eco) instead of the single type accent, so a day's climate curve is legible.
  • Presets are still indexed states, so conflict detection, jitter and base all work unchanged.
  • Maps to climate.set_temperature with hvac_mode; off → climate.turn_off.
# TYPE_REGISTRY — states carry parameters
"climate": {
  "label": "Climate", "icon": "mdi:thermostat",
  "param_schema": {                 # NEW
    "hvac_mode": ["off","heat","cool","auto"],
    "temperature": {"min":7,"max":35,"step":.5},
    "fan_mode": ["auto","low","med","high"],
  },
  "states": [
    {"key":"off","label":"Off","service":"climate.turn_off"},
    {"key":"heat","label":"Heat 21°",
     "service":"climate.set_temperature",
     "data":{"hvac_mode":"heat","temperature":21,
             "fan_mode":"auto"}},
  ],
},

Media player

Richer state

Segments become “play this, at this volume” windows across one or more speakers. Reuses HA's Media → Play media browser for source selection and adds a volume slider. A play state runs a short sequence of service calls, not just one.

daily-schedule-card · media bar

00:00 06:00 12:00 18:00 24:00
Kitchen speakers 2 speakers
media_player.kitchen · media_player.patio
Radio 25%
Evening playlist 40%

What changes

A new media picker field (opens HA's ha-media-player-browse) and a volume slider. The registry gains a sequence so one state can set volume then play.

  • Multiple targets already work — bar.targets[] is a list, so a speaker group needs no model change.
  • Off state pauses/stops (media_player.media_stop).
  • Volume + source live in the state's data, same pattern as climate.
# TYPE_REGISTRY — a state can run a sequence
"media": {
  "label": "Media player", "icon": "mdi:speaker",
  "states": [
    {"key":"off","label":"Stopped",
     "service":"media_player.media_stop"},
    {"key":"play","label":"Play",
     "sequence": [                    # NEW
       {"service":"media_player.volume_set",
        "data":{"volume_level":0.4}},
       {"service":"media_player.play_media",
        "data":{"media_content_id":"...",
                "media_content_type":"music"}},
     ]},
  ],
},

Automation triggers

New bar shape

A stateless bar: no on/off, no base fill. You drop trigger pins onto the timeline and drag them around; each fires an automation, scene or script at its time. This is the one that needs a second kind of bar.

daily-schedule-card · stateless trigger bar

00:00 06:00 12:00 18:00 24:00
Scene triggers stateless
fires: automation · scene · script
Wake
Lunch scene
Movie
Goodnight

What changes

The bar gains a kind. For "stateless", the segments[] array holds trigger points — an at time and an action, no end, no state, no base.

  • New track renderer: draggable pins instead of resizable blocks. The 15-min snap and jitter logic carry straight over.
  • The + button adds a pin at the largest gap; the editor picks the action to run.
  • No fill state ⇒ conflict detection is skipped for this kind (two triggers can share a moment harmlessly).
  • Engine fires a one-shot at each at (± jitter) rather than holding a state between boundaries.
# Bar model gains a kind; segments become points
"trigger": {
  "label": "Automation trigger",
  "icon": "mdi:map-marker-radius",
  "kind": "stateless",                # NEW
  "action_domains":
      ["automation","scene","script"],
},

01 — reusable

Param'd states

A param_schema on a type turns a state's data into editor fields. Built once, it serves climate and media — and unlocks the deferred dimmable-light / fan-% work in the handover.

02 — engine

Service sequences

Let a state run an ordered list of calls (sequence) so “set volume, then play” is one state. A small change to the boundary executor; every existing type stays single-call.

03 — model

Stateless bar kind

The only structural addition: bar.kind = "stateless", a pin renderer, and a one-shot fire in the engine. Isolated behind the kind flag, so range bars are untouched.
